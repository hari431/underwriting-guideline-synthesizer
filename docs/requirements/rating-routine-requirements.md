# Generic Rating Routine Requirements

## Purpose

Define how RateCraft should represent rating logic described in underwriting documents. A routine may contain assignments, formulas, lookups, conditions, branches, ordered steps, exceptions, rounding rules, and references to other rating assets.

These requirements are format-neutral. The example below is synthetic, and all factor values and calculation steps have been changed. It must not be treated as a production formula.

Status labels follow [README.md](README.md): **Implemented and verified**, **Best-effort**, **Unverified capability**, **Future work**.

## 1. What counts as a rating routine?

A routine is a described sequence of operations or rules that calculates, selects, adjusts, validates, or assigns a rating-related result.

A routine may be documented as a table of steps, narrative prose, flowchart, formula box, decision table, spreadsheet, or a combination of these. Do not assume a routine is always a single expression or that every routine has the same fields.

Routine identification and segmentation from source text is an **Unverified capability** (model-dependent). The extractor is instructed to emit one routine with ordered steps for a single sequential pipeline whose sub-steps feed into each other (including prerequisites stated adjacent to their use), rather than one routine per sub-step — but whether any given source is segmented correctly must be verified against its evidence.

## 2. Expected structured representation

**Implemented and verified** for the data model and deterministic handling; extraction fidelity is an **Unverified capability**.

For each routine, preserve the following fields when available:

| Field | Expected behavior |
|---|---|
| `id` | Stable internal identifier generated by the application (`R1…`; preserved when already assigned) |
| `name` | Source name, if present |
| `kind` | `formula`, `condition`, `calculation_steps`, or `worked_example`; recognized spellings normalize to these, anything else is preserved verbatim and warned about |
| `source_pages` | 1-based source page references (required; missing pages are an `error`) |
| `source_type` | Source kind when known (PDF ingest today) |
| `source_location` | Page, section, or cell range when stated |
| `evidence_text` | Verbatim supporting snippet (required in practice; missing evidence is a `warning`) |
| `expression_text` | Complete stated formula when the source provides one |
| `steps` | Ordered display texts in source order, preserving original numbering and gaps |
| `steps_detailed` | Structured per-step records (sequence, instruction, operation, expression, operand, inputs, output, dependencies, source pages/location, evidence, interpretation status, verbatim grid cells when the source lays a step across columns) |
| `conditions` | Decision-logic texts in source order |
| `conditions_detailed` | Structured per-condition records (condition, true/false branches, referral code, source pages/location, evidence, interpretation status) |
| `depends_on` | Referenced table/routine/variable names (display list) |
| `dependencies` | Structured dependency links (source, target, relationship type, explicit/inferred, evidence) |
| `inputs` / `outputs` | Values read / assigned by the routine; derived from the stated expression only when the source expression supports the parse |
| `purpose` | Description of the routine's role, if stated |
| `applicability` | Jurisdiction, coverage, product, transaction, or other scope when stated |
| `execution_context` | Per policy, per item, per location, per transaction, or other source-defined context |
| `notes` | Verbatim notes, including expected values for worked examples and flags for undefined symbols or conflicting variants |
| `review_status` | Extraction/review state |
| `confidence` | Extraction confidence when provided; low confidence warns |
| `issues` | Ambiguities, gaps, or conflicting descriptions (surfaced as validation issues, not stored on the routine) |

Do not create values merely to fill the schema. If a field is not present or cannot be confidently inferred, leave it unknown and explain why where useful.

## 3. Step representation

**Implemented and verified** for storage, normalization, and export; step parsing from prose is **Best-effort**.

Each step is a separate structured record with fields such as:

- `sequence`: original step number/order, preserving gaps when present.
- `instruction`: original instruction or target variable, if present.
- `operation`: assignment, arithmetic operator, lookup, condition, rounding, referral, or other operation as stated/inferred.
- `expression`: complete expression when explicitly provided or safely reconstructed from adjacent source steps.
- `operand`: source operand or value, preserving the original text.
- `inputs`: referenced variables, fields, parameters, or lookup keys.
- `output`: target variable or result, if present.
- `depends_on`: prior steps or assets when supported by the source.
- `source_pages`, `source_location`, `evidence`.
- `interpretation_status`: explicit, inferred, or needs review.
- `cells`: verbatim source grid cells by role when a step restates a grid row whose parts sit in separate columns; cells are evidence only and never become an operation, operand, or dependency by themselves.

Keep the original representation alongside any normalized interpretation. Do not silently replace source notation with a guessed formula.

Sparse explicit steps may be enriched from their own instruction text only (for example a prose lookup naming its table); explicitly provided fields are never overwritten, and entries without a confident parse stay minimal so nothing is invented. A step object carries an explicit operation only when the source states one; narrative sentences are kept verbatim without an invented operation, operand, or dependency. Lookup keys use the source column labels verbatim, never as object paths.

## 4. Supported patterns

The data model accommodates, when present (**Implemented and verified** as structures; recognition from source text is **Best-effort** or **Unverified capability** as noted):

- Assignments and initialization.
- Arithmetic operations, including addition, subtraction, multiplication, division, and other operators shown by the source.
- Table lookups with one or more lookup keys.
- UI or business inputs, policy attributes, schedule/item attributes, and intermediate values.
- Conditions, true/false branches, fallback rules, referrals, and exceptions.
- Ordered multi-step calculations.
- Rounding, caps, minimums, maximums, and thresholds.
- References to other routines, tables, or rating assets.
- Applicability and execution scope.
- Instructions whose meaning is not yet known (kept verbatim, flagged for review).

This list defines supported structures, not a requirement that every routine contain all of them.

## 5. Synthetic example — multi-step routine

The following example is deliberately changed and simplified to demonstrate the expected structure. It is not a real rating formula.

**Routine purpose:** Calculate an example item premium.

**Applicability:** Apply to each eligible scheduled item, using the item's associated location where relevant.

| Step | Instruction | Operation | Operand / expression |
|---:|---|---|---|
| 1 | Initialize `selected_limit` | Assignment | `0` |
| 2 | `selected_limit` | Assignment | Input parameter `coverage_limit` |
| 3 | `base_factor` | Table lookup | Lookup `Base Factor` using `territory_key` |
| 4 | `risk_modifier` | Table lookup | Lookup `Risk Modifier` using `company_key` and `risk_tier` |
| 5 | `package_adjustment` | Table lookup | Lookup `Package Adjustment` using `territory_key` |
| 6 | `unrounded_premium` | Expression | `base_factor × risk_modifier × package_adjustment × (selected_limit / 1000)` |
| 7 | `adjusted_premium` | Expression | `unrounded_premium × additional_adjustment` |
| 8 | `item_premium` | Rounding | Round `adjusted_premium` to the nearest whole currency unit |

Expected interpretation:

- Steps 1–2 initialize and then assign the limit from an input.
- Steps 3–5 are lookups, each with its own keys and referenced table.
- Steps 6–7 are calculations that depend on earlier results.
- Step 8 is a rounding operation.
- `additional_adjustment` is intentionally not defined here. The extractor must flag it as an unresolved input/dependency unless the source defines it elsewhere.
- The factors and sequence above are synthetic; they must not be copied into production logic.

## 6. Conditions and fallback behavior

For a source rule such as:

> If a selected territory is in the permitted set, use its corresponding factor; otherwise refer the case for manual review.

Expected structured representation (**Implemented and verified** as structures):

- Condition expression, preserving the permitted set.
- Action for the true branch.
- Action for the false branch.
- Referral code or reason if explicitly provided.
- Source evidence and location.
- Review flag if the actual factor mapping or referral behavior is not fully specified.

Do not collapse a condition into a blank expression or discard the fallback branch. Conditional language appearing only inside unstructured steps (without structured conditions) raises a warning that names the gap without guessing the fallback.

## 7. Dependencies and unresolved logic

**Implemented and verified** for representation and deterministic checks; dependency discovery from prose is **Best-effort**.

- Represent dependencies as individual links/records, not one flattened string.
- Preserve references to tables, routines, variables, inputs, and prior steps.
- Distinguish a source-explicit dependency from one inferred by following a variable reference.
- Flag references to undefined variables or missing assets.
- Preserve unfamiliar legacy instructions verbatim and flag them for analyst review.
- Never invent the meaning of an unknown operator, abbreviation, or external routine.

Resolution uses only explicit evidence (own lookup steps, unique routine outputs, explicit table dependencies); anything else is reported as an input parameter only when no sources are evidenced (or the value is a known lookup key), otherwise marked unresolved rather than guessed. Alternative or conflicting formulas for the same result are all preserved verbatim and flagged instead of choosing one. Symbols defined nowhere in the source are kept verbatim and flagged as undefined in notes.

Deterministic routine grouping is **Best-effort**: adjacent single-expression routines merge into one multi-step routine only on strong structural evidence (numbered chains with consecutive numbers and handoff links, or adjacent prerequisite pairs with forward-reference evidence), ordered producer-first, and every grouping adds a verification warning. Ambiguous sequences pass through untouched.

## 8. UI and Excel export requirements

**Implemented and verified.**

The UI makes it possible to inspect the routine summary and its ordered steps: Browse tabs list routines with search, filters, and pagination; each routine opens a detail editor with source pages and collapsible evidence; the grouped Review view shows one collapsed card per routine needing review with each issue once and navigation back to the routine detail.

Workbook layout (actual; deterministic build):

1. **Routine Summary** — one row per routine (ID, Name, Kind, Purpose, Applicability, Execution context, Inputs, Outputs, Expression, Source pages, Source location, Evidence text, Notes, Review status); names hyperlink to the routine sheets.
2. **One sheet per routine** (in job order; safe unique names up to 31 characters):
   - Stepwise routines (has steps or an expression, except `condition` kind): ordered **Steps** (`Step #`, `Instruction`, `Op`, `(`, `Operand`, `)`, `Line Comment`) with one row per operation, explicit brackets, and hierarchical numbers (`5.1`, `5.2`) for expanded source steps so reassembling the rows reproduces the source expression; conditionals as `IF`/`ELSEIF`/`ELSE`/`ENDIF` rows with one row per branch assignment; unparsed steps show `REVIEW` in `Op` with a needs-review comment; worked examples add an **Inputs** block (`Input`, `Source`, `Lookup keys`); then **Conditions**, **Unresolved items**, **Source evidence**.
   - `condition` routines and routines with neither steps nor expression (legacy layout): **Inputs**, **Steps** (`Step #`, `Instruction`, `Operation`, `Operand`, `Comment`), **Final calculation** (`Calculation`, `Output`), **Conditions**, **Dependencies** (`Target`, `Type`, `Explicit/Inferred`, `Variable / Keys`), **Unresolved items**, **Source evidence**.
3. **Issues** — validation issues including unresolved dependencies and ambiguous steps.

The exporter never flattens ordered steps, dependencies, or branches into pipe-separated text. The UI and workbook represent the same reviewed records.

Shared cross-routine "Routine Steps" / "Dependencies" / "Conditions" grids are **Future work** — not implemented; per-routine sheets plus the Routine Summary and Issues sheets serve that role today.

## 9. Acceptance checks

- Original step order and numbering are preserved, including gaps.
- Multi-step calculations are not reduced to a single vague sentence.
- Every lookup retains its keys and referenced asset when available.
- Conditions preserve both branch and fallback behavior.
- Dependencies are represented as separate relationships.
- Unknown or undefined inputs are flagged, not invented.
- Source evidence is linked to the relevant routine/step.
- Exported routine data matches the reviewed UI data.
- No production behavior depends on the synthetic example names, factors, or steps.
