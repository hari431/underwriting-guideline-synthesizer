# Generic Rating Table Requirements

## Purpose

Define how RateCraft should identify, structure, validate, review, and export rating tables from underwriting guidelines.

These requirements are format-neutral. Examples below are synthetic and intentionally use changed names and values. They are not production rates or instructions to implement a particular insurance platform.

Status labels follow [README.md](README.md): **Implemented and verified**, **Best-effort**, **Unverified capability**, **Future work**.

## 1. What counts as a rating table?

A rating table is structured data used by a rating process to look up a rate, factor, cost, threshold, limit, modifier, or other value. A source may contain one or more tables, and tables may be embedded in PDFs, appendices, or separate documents.

Do not assume every table has the same name, number of columns, key fields, data types, or layout.

Table identification from source text is an **Unverified capability** (model-dependent): the extractor is instructed to record a grid as a rating table only when it is reusable lookup data keyed by its columns, and to keep one-instance worked illustrations in routine evidence/notes instead. A grid computed for a single instance with a computed total is not a reusable rating table. Deterministic checks flag suspected instance breakdowns for review (best-effort heuristic).

Spreadsheet workbooks as an upload source are **Future work**: ingest accepts text-based PDFs only. The data model preserves a `source_type` field for later sources.

## 2. Expected structured representation

**Implemented and verified.**

For each table, preserve the following fields when available:

| Field | Expected behavior |
|---|---|
| `id` | Stable internal identifier generated by the application (`T1…`; preserved when already assigned) |
| `name` | Display title from the source; when the source labels a grid with an asset code or ID, the code stays in the name alongside the descriptive title so references to the code resolve |
| `aliases` | Distinct source labels for the table (never duplicating the display name); embedded asset codes answer as aliases so dependency references resolve |
| `source_pages` | 1-based source page references (required; missing pages are an `error`) |
| `source_type` | Source kind when known (PDF ingest today; other sources are future work) |
| `source_location` | Page, section, or cell range when stated |
| `evidence_text` | Verbatim supporting snippet (required in practice; missing evidence is a `warning`) |
| `headers` / `columns` | Ordered source column labels plus per-column definitions (label, original label, order, inferred type, role, units, evidence when supported) |
| `rows` | Complete ordered set of data rows; every cell preserved as text |
| `purpose` | Description of what the table is used for, if stated |
| `applicability` | Jurisdiction, coverage, business segment, or other applicability, if stated |
| `effective_period` | Effective date or period, if stated |
| `footnotes` / `notes` | Notes that qualify the table or its values |
| `continuation` | Continuation / logical-group linkage when supported (split parts, related tables) |
| `review_status` | Extraction/review state |
| `confidence` | Extraction confidence when provided; low confidence warns |
| `issues` | Missing, conflicting, ambiguous, or suspicious data (surfaced as validation issues, not stored on the table) |

Use optional fields only when supported by the source. Do not fabricate a title, purpose, applicability, effective date, or other metadata.

## 3. Column definitions

**Implemented and verified** for preservation; **Best-effort** for inference.

For each column, preserve:

- Original column label and order.
- Inferred data type, with confidence or review status if uncertain.
- Units, currency, percentage/factor meaning, and formatting where supported.
- Whether the column appears to be a lookup key, output value, descriptive field, or unknown role.
- Source evidence for inferred meaning.

Do not silently rename source columns. A normalized display label may be added, but the original label must remain available (the implementation keeps `original_label` beside `label`).

Column type/role/unit inference is deterministic and best-effort: it fires only on structural evidence (header wording, numeric shape) and its output is exported for review rather than asserted as fact.

## 4. Data-row preservation

**Implemented and verified** for storage and export; extraction fidelity is an **Unverified capability**.

- Preserve every row and every column value.
- Preserve numeric precision and distinguish a numeric value from a percentage or multiplier.
- Preserve identifiers with leading zeros as text when appropriate.
- Preserve negative values, blanks, explicit zeroes, ranges, and special values distinctly.
- Preserve row order unless the source clearly defines another ordering rule.
- Do not deduplicate apparently repeated rows without flagging them and retaining the source data.
- Do not infer missing cells from nearby rows.
- Support tables that continue across pages. Record continuation and evidence links when the source supports them (the implementation also links split parts of one logical table via `continuation`, filling only absent values).
- Keep explanatory text, import instructions, and metadata separate from the actual rating-data rows.

Short rows (fewer values than headers) are kept positionally and flagged with a misalignment warning that names no column as the gap site, because the gap may sit anywhere in the row.

## 5. Synthetic example — multi-key factor table

The following is a deliberately changed example only.

**Table title:** Example Deductible Modifier

| Region key | Deductible band | Risk group | Modifier |
|---|---|---:|---|---:|
| R-A | 750 | Group 1 | 0.037 |
| R-A | 750 | Group 2 | 0.029 |
| R-A | 1500 | Group 1 | 0.033 |
| R-B | 750 | Group 1 | 0.041 |

Expected interpretation:

- There are three potential lookup keys and one output value.
- The modifier values are examples, not real rating factors.
- `750` and `1500` are numeric deductible values; `R-A`, `R-B`, and `Group 1` are identifiers.
- The application must not assume that every table uses three keys or a column named `Modifier`.

## 7. Validation and analyst review

**Implemented and verified** (deterministic; no model calls). Policy: structural/traceability breaks are `error` issues; everything interpretive is a `warning` flagged for review, never treated as invalid.

Errors (block Excel export until fixed):

- Missing source page reference.
- Source pages beyond the document length.
- Empty table (no headers and no rows).

Warnings — flag rather than silently repair:

- Missing or duplicated column labels; blank labels.
- Rows with an unexpected number of values; short-row misalignment.
- Duplicate rows (retained, not deduplicated).
- Conflicting values for the same apparent lookup key.
- Unclear units or unclear factor semantics.
- Suspected continuation tables whose relationship is uncertain.
- Missing key or output values in role-carrying columns; blank cells where other rows have values.
- Numeric-looking identifiers that could lose leading zeros.
- Mixed negative/positive values, non-numeric values in otherwise-numeric columns, overlapping range bands — noted without assuming they are wrong.
- Explicit missing-value markers in the source (preserved and flagged, not filled).
- Suspected merged adjacent grids (blank separator row/column, repeated headers, embedded single-value rows, record-style columns); suspected one-instance breakdowns; unexpanded single-column `label: value` text.
- Low extraction confidence; reported contradictions or ambiguities carried in table text.

Validation distinguishes a definite structural error from a domain-specific value that merely looks unusual. Reviewer edits re-run validation only and never call the model.

## 8. UI and Excel export requirements

**Implemented and verified.**

The UI and Excel export use the same reviewed structured record.

UI behavior:

- Browse tabs list tables with search (ID/name), filters (all / with warnings / unresolved), and pagination.
- Each table opens a detail editor (title, headers, cells) with source pages and collapsible evidence.
- The grouped Review view shows one collapsed card per table needing review, with each issue once, full text, and evidence; cards link back to the table detail.
- Save actions re-validate locally; export stays available with warnings and is blocked only by errors.

Workbook layout (actual; deterministic build, fixed timestamps):

1. **Cover** — document name, page count, extraction source, counts, and linked lists of tables/routines.
2. **Table Summary** — one row per table (ID, Title, Aliases, Purpose, Applicability, Effective period, Source pages, Source location, Evidence text, Footnotes, Notes, Continuation, Row count, Column count, Review status); titles hyperlink to the table sheets.
3. **Routine Summary** — routine index (see routine requirements).
4. **Table Columns** — one row per column definition (Table ID, Table title, Column #, Original label, Display label, Inferred type, Role, Units, Evidence).
5. **One sheet per rating table** (in job order; safe unique names up to 31 characters) — title in the first row, header row, then data rows only. No export-only columns, no packed pipe-separated rows, no repeated metadata.
6. **One sheet per routine** (see routine requirements).
7. **Issues** — one row per validation issue (Issue ID, Severity, Target type, Target ID, Message, Source pages).

The exporter preserves every original column and value without loss and invents no platform-specific metadata fields. Sheet order is Cover, Table Summary, Routine Summary, Table Columns, per-table sheets, per-routine sheets, Issues.

Shared "Table Data" / "Evidence and Issues" grids across tables are **Future work** — not implemented; per-table sheets plus the Table Columns and Issues sheets serve that role today.

Deterministic table reshaping is **Best-effort** and always flagged: side-by-side grid separation and single-column `label: value` expansion fire only on strong structural evidence and each adds a verification warning; ambiguous layouts pass through untouched for the validator to flag.

## 9. Acceptance checks

- All source rows and columns are accounted for.
- Leading zeros and numeric precision survive extraction and export.
- Metadata/instructions are not mixed into the data rows.
- Multi-page tables retain their source references.
- Uncertain interpretations are visible for review.
- Exported data matches the reviewed UI data.
- No production behavior depends on the synthetic example names, keys, or values.
